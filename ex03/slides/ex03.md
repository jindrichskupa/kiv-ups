# Příklad 1 - bajty z `DataOutputStream`

```java
DataOutputStream out = new DataOutputStream(sock.getOutputStream());
out.writeInt(258);
out.writeShort(-2);
out.writeBoolean(true);
out.writeUTF("Ahoj");
out.writeBytes("OK\n");
out.flush();
```

- a) Zapište hexadecimálně všechny bajty, které odejdou. Kolik jich je?
- b) Druhá strana pošle text `KIVU` a Java na něj zavolá `readInt()`. Co přečte?

---

# Řešení 1

```
writeInt(258)        00 00 01 02          258 = 0x0102, 4 B, big-endian
writeShort(-2)       FF FE                dvojkový doplněk, 2 B
writeBoolean(true)   01
writeUTF("Ahoj")     00 04 41 68 6F 6A    2 B délka + bajty
writeBytes("OK\n")   4F 4B 0A             jen dolní bajt každého znaku
```

- a) celkem **16 B**
- b) `4B 49 56 55` → `0x4B495655` = **1 263 097 429** - Java nepozná, že to byl text

<small>Pozn.: Java (`Data*Stream`) používá síťové pořadí bajtů (big-endian) - stejné jako `htonl` v C. Proto se s C serverem domluví, pokud C strana nezapomene na `ntohl`.</small>

# Příklad 2 - C server čte Javu

Java klient pošle `writeInt(258)` a `writeShort(-2)`, C server na x86 čte:

```c
int x;
short y;
recv(c, &x, 4, 0);
recv(c, &y, 2, 0);
printf("%d %d\n", x, y);
```

- a) Co server vypíše?
- b) Opravte kód. Co dalšího může selhat?

---

# Řešení 2

- a) **`33619968 -257`** - bajty `00 00 01 02` přečte little-endian jako `0x02010000`, `FF FE` jako `0xFEFF`
- b)

```c
uint32_t nx; int16_t ny;
if (recv_all(c, &nx, 4) != 4) …;   /* recv může vrátit méně než 4 B! */
if (recv_all(c, &ny, 2) != 2) …;
int32_t x = (int32_t)ntohl(nx);    /* 258 */
int16_t y = (int16_t)ntohs(ny);    /* -2 */
```

<small>Pozn.: `recv_all` = smyčka, která volá `recv`, dokud nemá požadovaný počet bajtů (nebo nevrátí 0/-1). Použijte pevné typy `int32_t`, `uint16_t` - `int` a `long` mají na různých platformách různou velikost.</small>

# Příklad 3 - text a konce řádků

```java
PrintWriter w = new PrintWriter(sock.getOutputStream());
BufferedReader r = new BufferedReader(new InputStreamReader(sock.getInputStream()));
w.println("LOGIN pepa");
String odp = r.readLine();
```

C server čte po bajtech do `\n`, porovná řádek s `"LOGIN pepa"` a odpoví `OK\n`.

- a) Klient i server "zamrznou". Proč?
- b) Po opravě a) to funguje v Linuxu, ale ne ve Windows. Proč?
- c) Co udělá `readLine()`, když server pošle `OK` bez `\n`? A když `OK\r\n`?

---

# Řešení 3

- a) `PrintWriter` bez autoflush data jen **bufferuje** → nic neodešlo, server čeká na `\n`, klient na odpověď (deadlock); opravit `w.flush()` nebo `new PrintWriter(out, true)`
- b) `println` píše systémový konec řádku: Windows **`\r\n`** → server dostane `"LOGIN pepa\r"`
- c) bez `\n` **čeká navždy** (nebo do zavření spojení); `\r\n` i samotné `\r` odstraní a vrátí `"OK"`

<small>Pozn.: v protokolu vždy přesně definujte konec řádku a posílejte ho explicitně: `w.print("LOGIN pepa\n"); w.flush();`. Kódování také explicitně: `new OutputStreamWriter(out, StandardCharsets.UTF_8)`.</small>

# Příklad 4 - Python `struct`

```python
import struct
a = struct.pack('!HI', 4242, 1)
b = struct.pack('<HI', 4242, 1)
c = struct.pack('HI', 4242, 1)
x = struct.unpack('!I', b'\x00\x00\x01\x02')[0]
```

- a) Jaké bajty a kolik jich je v `a`, `b`, `c`? Jaká je hodnota `x`?
- b) Proč `s.send(a)` nestačí a co použít? Co může vrátit `s.recv(4)`?

---

# Řešení 4

```
a  = 10 92 00 00 00 01              6 B   ! = síťové pořadí, bez zarovnání
b  = 92 10 01 00 00 00              6 B   < = little-endian, bez zarovnání
c  = 92 10 00 00 01 00 00 00        8 B   nativní pořadí I zarovnání (2 B výplň)
x  = 258
```

- b) `send` může odeslat jen část a vrátí kolik → **`sendall`**; `recv(4)` vrátí **1 až 4 B**, nebo `b''` při zavření spojení → číst ve smyčce

<small>Pozn.: formát bez prefixu (`'HI'`) se chová jako struktura v C na daném počítači - včetně výplně. Pro síť vždy `!`.</small>

# Příklad 5 - C# `BinaryWriter`

```csharp
var w = new BinaryWriter(stream);
w.Write(258);
w.Write((short)-2);
w.Write("Ahoj");
```

- a) Jaké bajty odejdou?
- b) Co přečte Java klient přes `readInt()`, `readShort()`, `readUTF()`?
- c) Jak poslat `258` v síťovém pořadí?

---

# Řešení 5

- a) `02 01 00 00` · `FE FF` · `04 41 68 6F 6A` - **little-endian**, délka řetězce jen 1 B
- b) `readInt` = `0x02010000` = **33 619 968**, `readShort` = `0xFEFF` = **−257**, `readUTF` čte 2 B délky `04 41` = 1089 → čeká na dalších 1089 bajtů
- c) `w.Write(IPAddress.HostToNetworkOrder(258))` nebo `BinaryPrimitives.WriteInt32BigEndian(buf, 258)`

<small>Pozn.: `BinaryWriter.Write(string)` píše délku jako 7bitové proměnné číslo (do 127 znaků 1 B), `writeUTF` v Javě vždy 2 B. Formáty se jmenují podobně, ale nejsou kompatibilní.</small>

# Příklad 7 - co se skrývá pod obalem?

Doplňte, které BSD volání z minula odpovídá kterému kódu:

<style scoped>table { font-size: 19px; }</style>

| Java | Python | C# | BSD |
|------|--------|----|-----|
| `new ServerSocket(4242)` | `s = socket.socket(); s.bind(('', 4242)); s.listen()` | `new TcpListener(IPAddress.Any, 4242).Start()` | ? |
| `ss.accept()` | `conn, addr = s.accept()` | `listener.AcceptTcpClient()` | ? |

# Řešení 7

<style scoped>table { font-size: 19px; }</style>

| obal | BSD |
|------|-----|
| `new ServerSocket(4242)`, `TcpListener.Start()` | `socket` + `setsockopt(SO_REUSEADDR)`* + `bind` + `listen` |
| `accept()`, `AcceptTcpClient()` | `accept` - vrací nový objekt = nový socket |
| `new Socket("zcu.cz", 4242)`, `new TcpClient(…)` | `getaddrinfo` (DNS) + `socket` + `connect` |
| `read`, `recv`, `Read` | `recv` - vrací 1 až n bajtů, konec spojení zvlášť (-1 / `b''` / 0) |
| `close`, `Close` | `close` / `closesocket` |

<small>Pozn.: * záleží na jazyce a platformě. Konstruktor v Javě a C# provádí několik volání najednou včetně DNS - proto může házet `UnknownHostException` nebo `SocketException` už při vytvoření objektu.</small>

# Řešení 10 (bonus)

# Příklad 11 - vlákna a virtuální vlákna (bonus)
<!-- bonus -->

Java server vytváří vlákno pro každého klienta, výchozí zásobník platformového vlákna je 1 MB.

- a) Kolik virtuální paměti rezervuje 10 000 klientů?
- b) Co se změní s `Thread.startVirtualThread(…)`?
- c) Vadí v Pythonu GIL serveru, který hlavně čeká na sockety?

---

# Řešení 11 (bonus)
<!-- bonus -->

- a) 10 000 · 1 MB ≈ **10 GB** virtuální paměti (+ 10 000 vláken operačního systému)
- b) virtuální vlákno má zásobník na haldě, řádově **jednotky kB**; při blokujícím `read` se odpojí od vlákna OS a to zatím obslouží jiné → 10 000 klientů ≈ desítky MB
- c) **nevadí** - při čekání na `recv` se GIL uvolní; vadil by u výpočetně náročné logiky

<small>Pozn.: virtuální vlákna (Java 21+) a `async`/`await` v C# umožňují psát jednoduchý blokující kód "vlákno na klienta" i pro tisíce klientů.</small>

# Řešení 13 (bonus)
<!-- bonus -->

```java
for (;;) {
    p.setLength(buf.length);              // receive zkrátí délku paketu na poslední datagram!
    ds.receive(p);
```

# Shrnutí

- všude pod tím jsou BSD sockety: `recv` vrací část dat, konec spojení je zvláštní hodnota
- síťové pořadí = big-endian: Java `Data*Stream` ano, C# `BinaryWriter` a nativní `struct` ne
- text: explicitní konec řádku (`\n`) a kódování (UTF-8), délky v bajtech
- `flush()` po každé zprávě; Python `sendall` místo `send`
- serializace specifická pro jazyk (`ObjectOutputStream`) se s C nedomluví

# Slovníček zkratek

<style scoped>table { font-size: 19px; }</style>

| zkratka | význam |
|---------|--------|
| big-endian, little-endian | nejvyšší / nejnižší bajt na nejnižší adrese (síť / x86, ARM) |
| UTF-8, UTF-16, ASCII | kódování znaků: proměnná délka 1–4 B, 2 nebo 4 B, 7 bitů |
| modified UTF-8 | varianta UTF-8 pro `writeUTF` (nula jako 2 B, 2B délka před řetězcem) |
| GIL | Global Interpreter Lock - v jednu chvíli běží Python kód jen v jednom vlákně |
| JVM | Java Virtual Machine |
| DNS | Domain Name System - překlad jmen na adresy |
| TCP, UDP | spojovaný proud bajtů, nespojované datagramy |
| `serialVersionUID` | verze třídy pro Java serializaci |
| GZIP | kompresní formát (`GZIPOutputStream`, `GZipStream`) |
| TLS / SSL | šifrovaná vrstva nad TCP (`SSLSocket`, `SslStream`, `ssl`) |
